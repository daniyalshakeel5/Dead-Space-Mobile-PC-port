# Dead Space Mobile — Native Windows/Linux PC port handoff

## Receiver activation and native mode state — November 1, 2026

Original-APK evidence
[41334190135](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41334190135)
proved the original parser owner vtable `0x00489670` maps
method `+0x64 -> 0x00278E58`, reset `+0x28 -> 0x00273A0C`
and owner follow-up `+0x70 -> 0x00276D18`.
Original ARM `0x278018` enters method `+0x64` from
`0x2786F0` when owner byte `+0x8B6` is zero. This is
**the default constructor state**; the previously implemented
owner `+0x8B6 != 0` UTF-16 lookup path is not automatically
active at startup.

Original run
[41334587719](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41334587719)
confirmed `0x278E58` calls `0x273570(owner+0x8BC,
root-at-owner+0x8C8)` to release any old nodes. That
destructor recursively invokes original game memory-provider
virtual methods for a nonempty tree; cannot simply free arbitrary
mapped ARM nodes. After cleanup, `0x278E58` sets
`[owner+0x8C0]=[owner+0x8C4]=ownerVA+0x8C0`,
`[owner+0x8C8]=0`, owner byte `+0x8B6=0`,
byte `+0x8CC=0` and word `+0x8D0=0`.
If owner `+0x8AC` is null, it branches to the original
cleanup/return; if non-null, it calls provider vtable
`+0x14` followed by further owner methods and substantial
resource parsing. The native implementation intentionally
**does not claim provider activation**.

`src/original_receiver_activation.cpp` now reproduces
the 0x278E58 mapped-owner state transitions in native C++,
safely skips destructor work only for an empty tree and
requires a genuine separate original 0x273570 destructor for
nonempty trees. It returns a *distinct* status when the
non-null provider branch is reached. The original
`0x2786F0` branch in `src/original_receiver_prefix.cpp`
now calls this native activation when supplied; it cannot
mistake a reset for successful resource insertion.

Original `0x26C410` sets the receiver's mode and parser
parameter. The exact ARM semantics are: `r1==1` writes
the boolean version of r2 to byte `+0x8B5`, calling
the owner's vtable `+0x28` when changing to zero;
`r1==2` writes raw r2 to word `+0x8B8`.
`src/original_receiver_mode.cpp` now implements both
original machine-level branches and rejects an unrecovered
reset service rather than falsely advancing. Original
resource loader `0x286918` calls `0x26C410`
with r1=1, r2=1, after constructing the receiver and
before invoking `0x278778`.

Verified Windows/Linux CTest:
[41335144028](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41335144028)
**56/56 tests passed** with the native activation
and mode-setting regressions. These tests remain isolated
synthetic tests; native engine boot is blocked by
the still-untranslated original provider and renderer.

## Native record replacement and receiver identity — November 1, 2026

Original ELF ARM `0x28611C` compares the length of UTF-8 text
converted by `0x28CC88` to the current UTF-16 destination length,
resizes only as needed using the original grow policy, overwrites
the destination, then writes a 16-bit terminator. The native
`src/original_record_text.cpp` now implements this actual mutable
UTF-16 behavior with an owned `std::u16string`, tracking the
original logical capacity in code units. Its regression tests cover
grow, shrink, overwrite, original UTF-8 decoding quirks and malformed
input without destructively overwriting old data.

Original `0x2862E8` initializes a UTF-16 temporary through
`0x285590`, replaces that temporary text from a UTF-8 resource
range using `0x28611C`, then invokes the receiver's vtable slot
`+0x58` with decoded UTF-16 text, literal tag and original
caller argument. Native
`src/original_record_insert.cpp` now reconstructs this outer
call and actual data transformation. The still-unported vtable
handler is an explicit required dependency, not a fictional
successful record insertion.

## Native token lookup and UTF-8 record text — November 1, 2026

Native token membership now replaces the original 0x285630
character conversion plus its 0x2854B8 bytewise sorted-tree lookup.
Original-APK research runs
[41330960106](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41330960106)
and
[41331060172](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41331060172)
show that 0x285630 copies an input C string, maps every byte via
the original GOT-loaded 16-bit character table at byte*2+2, and
searches a sorted tree through 0x2854B8. The lookup compares the
shorter of the two byte ranges using original memcmp, then length;
the native equivalent uses `OriginalUnsignedByteLess`.

`src/original_resource_token_lookup.cpp` supplies a native ordered
token index and lookup. The index accepts keys supplied by actual
parsed game resources and never invents the original key set.
Mapped game char-table bytes are required; the code never assumes
ASCII-specific folding. The native lookup is synthetic-fixture tested,
not yet connected to a fully operational 0x2863EC parser.

The original helper 0x28CC88, called twice by 0x28611C, was recovered
in [41331391711](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41331391711).
The numeric UTF-8 validation table was independently read from the
original ELF in
[41331509759](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41331509759).
Valid lead bytes: ASCII 0x01..0x7F, C2..DF (2 bytes), E0..EF (3),
F0..F4 (4); continuation bytes must be 80..BF. The original 0x28CC88
counts 16-bit output units if r0=0 and writes them if r0!=0.
Original behavior worth preserving: input ASCII NUL stops conversion,
invalid leading/continuation/truncated sequences return r0=-1,
a decoded scalar outside the non-overlong Unicode range stops
conversion *normally* with the preceding-unit count, and a four-byte
scalar is written as **one truncated 16-bit code unit**, not a
surrogate pair.

`src/original_resource_utf8_decode.cpp` now implements this exact
native decode/count behavior, including output buffer capacity and
terminator semantics. It supplies the 0x28611C two-pass resource
text conversion into owned native `std::u16string` storage.
This is not a claim that 0x28611C's entire record mutation or
0x2862E8's insertion is done. The actual parser's object lifetime,
original token set creation, record dispatch, tree nodes and
virtual owner methods remain unresolved.

Windows/Linux CTests for token mapping, UTF-8 validation,
bounds, four-byte truncation, original early termination, and
two-pass decoding are located in
`tests/original_resource_token_lookup_tests.cpp` and
`tests/original_resource_utf8_decode_tests.cpp`.
The tests use independent small synthetic data and do not establish
that the game boots.


## Original parser 0x2863EC: native text processing (November 1)

The verified original-APK ARM analysis from
[run 41329810957](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41329810957)
and
[run 41329931129](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41329931129)
shows that 0x2863EC creates temporary string objects, processes resource
buffer intervals, calls 0x285918 to append missing bytes, then calls
0x2857A0, 0x285238 and token dispatch/record helpers. This is
a more complex parser than a resource-tree constructor.

Native `src/original_resource_byte_string.cpp` now reconstructs the
observable byte-string behavior of 0x285918: append a byte range;
preserve its terminating NUL; and use the ARM grow policy of
max(required_bytes, 8 if old_capacity<=8 else 2*old_capacity)
plus one terminator byte. It safely handles self-aliasing and
bounded native allocations. Native
`original_complete_parser_range_0x2863ec` implements the original
two branch paths at 0x2863EC: only append the suffix of the resource
source range not already buffered by the current temporary string.
This code processes actual caller-supplied mapped resource bytes,
not dummy engine callbacks.

Original 0x285590 is used by the record insertion path at 0x2862E8.
Native `src/original_resource_utf16.cpp` reconstructs its little-endian
two-byte unit copy and trailing UTF-16 terminator with
`std::u16string`. Odd/truncated byte ranges are rejected instead of
silently truncating. The original ARM allocator and its physical
32-bit pointer layout are deliberately replaced by native owned
storage. Both routines have CTest coverage for real data copying,
capacity boundaries, error cases, and embedded NUL data.

Remote research and native CTests are verification of the *isolated
recovered semantics*, not real game-engine initialization. The
remaining major 0x2863EC dependencies include string delimiter helper
0x2857A0, resource token matcher 0x285630, UTF-16 mutation helper
0x28611C, resource record dispatch/insertion 0x2862E8 and
original vtable methods; they must produce real parsed resource trees
before the native three-pass 0x286918 registration can execute end
to end on the user's asset data.


## Original resolver and resource-tree loader integration — November 1

### Verified ARM evidence and native resolver

Original-APK remote trace [41327755219](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41327755219)
contains original 0x28A718 through its return at 0x28A864. Native
`src/original_resource_resolver.cpp` implements the verified outer
call order, branch results and buffer zeroing:

- 0x276CB4 allocates 0x14 bytes for resource pool (r1=owner).
- 0x275680 initializes a 0x400-byte buffer; original Bionic memset
  zeroes the buffer before the next object is initialized.
- 0x27E8E8 allocates a separate 0x30-byte object; 0x26D35C and
  0x26D23C initialize it with original mode=1 and float32 1.0.
- 0x27B204 copies the name and 0x272DDC performs lookup with original
  arguments (r1=1,r2=6,r3=1,stack0=0).
- On a nonzero lookup, 0x2716F8 produces a count and scratch output;
  the object vtable +0x3C is called. Its +0x2C is invoked only when
  that count differs from 0x2710.
- Original 0x27744C releases scratch; even for a **zero lookup**,
  the function returns the separate 0x30-byte object rather than null.

The outer resolver is called by the native 0x28B3A4 mode-one factory.
Underlying original allocator, lookup, object initialization and
virtual-method implementations remain missing. The C++ callback
interfaces must be bound to genuine native implementations before
declaring that the resource is truly loaded. Test fixtures do not
satisfy this engine requirement.

### Three actual resource-registration passes

Original-APK remote run [41328165251](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41328165251)
proved tree header 0x283408 is exactly `r0+4`, and 0x2933EC follows
ARM32 tree left/right/parent links (0/4/8). Native equivalents are in
`src/original_resource_tree.cpp`.

Original 0x286918 visits three tree containers at parsed scratch
offsets +0x28, +0x50 and +0x78, retrieves the first node from
`[container+0x0c]`, and terminates at `container+0x08`.
Every node supplies the resource source address at +0x10 and
descriptor at +0x24. It invokes original 0x284178 at addresses
0x2869A8, 0x2869E4 and 0x286A20 respectively, then 0x2933EC to
advance. These three tree traversals and actual native C++
registration semantics are implemented in
`src/original_parsed_tree_registration.cpp`, without executing ARM.

**Scope boundary:** The preliminary 0x286918 parser calls
0x27A768, 0x26C410, 0x278778 and 0x2863EC and later teardown remain
unported; these must produce real parsed resource trees before
this new native registration phase can process real game content.
Do not bypass these dependencies or claim an engine boot.

## Native original-resource registration update — 2026-11-01

The real APK's entire ARM `0x284178` control flow is now inspected,
including `0x2839C8` precheck, conditional `0x283F5C` removal,
`0x281DF4` temporary string construction, byte conversion via the
original table at GOT slot `0x004909F4`, `0x2837B4` pair insertion,

converted names and descriptor values from original private mapped

`0x281DF4` ARM allocator.

**Engine state is not initialized yet.** The native resource table

  `original_followup_store_0x2833f4` is in
  `src/original_stage_zero_followup.cpp`. Tests cover byte order,
  unaligned host memory, zero and bit patterns, minimal destination size,
  and absence of unrelated writes.
- **ELF 0x0028ca24: complete selected type-2 case only.** The original
  `0x00280520` caller ALWAYS supplies type 2. Verified ARM case first
  stores the literal IEEE754 float **1.0** (`0x3F800000`) at +0x14,
  writes type 2 at +0x10, then overrides +0x14 with the live
  32-bit floating-point bits from original ELF VA **0x0049CD1C**.
  `src/original_stage_zero_type_two.cpp` preserves float bit patterns
  exactly. No other switch cases are claimed recovered.
- **ELF 0x00281d54: post-allocator semantics reconstructed.** The
  original calls an unresolved owner vtable method at offset +0x0C to
  allocate a record. It then conditionally initializes exact fields
  at record +0x04,+0x08,+0x0C,+0x10 (single byte),+0x14,+0x18,+0x1C
  and stores the original 32-bit record pointer (or zero on null
  allocation) in original global slot **0x0049CB94**.
  `src/original_record_postalloc.cpp` reconstructs ONLY this proven
  postreturn behavior. The virtual allocation method, allocation size,
  and returned pointer ownership are **not** guessed.
- **Unified native ARM global map.** Original shared frame-state base
  `0x0049CAA8` has verified record slot +`0xEC` and type-2 float
  field +`0x274`, both independently recovered by PC-relative ARM
  literal resolution. `src/original_runtime_globals.cpp` maps the
  caller-provided original global bytes using bounds checks and preserves
  original ARM 32-bit address tokens without host pointer casts.
- Integrated `original_execute_stage_zero_setup_with_recovered_type_two`
  calls both completely recovered functions directly, reads the live
  mapped float bytes, preserves gettimeofday's one-time clock seed
  guard, invokes the *still-missing* `0x281d54` only when its real
  behavior is supplied, and reloads `context+4` after that callback.
  No texture viewer, substitute gameplay loop or ARM emulator.
- **Verification:** [real original APK ARM instruction and global-offset
  proof](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41303277886)
  passed; [Windows/Linux original C++ core CTests](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41303281901)
  passed at the latest branch revision during this checkpoint.

- **Complete original allocator CALLSITE and post-return behavior** is
  implemented in `src/original_allocator_call.cpp`. Recovered from actual
  ARM `0x00281D54`: owner pointer loaded from `context+4`; original
  owner vtable loaded from `[owner+0]`; virtual function selected at
  `[vtable+0x0C]`; ABI arguments are

  verified by original APK ELF instructions/literals in

  The **actual virtual allocation method remains unknown and NOT
  implemented**. A caller-supplied verified callback is required;
  unknown functions do not silently fall back to host `malloc`.
- **Engine singleton / original allocator owner upstream:** Original ARM
  `0x0027E930` performs the runtime interface lookup using pointer
  from BSS/global at **0x0049CAA0**, request ID **0x10004**,
  and vtable method at **+0x18**. The GOT points into runtime BSS,
  not file-backed ELF data, so its actual runtime object value cannot
  be deduced from the APK alone. The stage-zero constructor
  `0x0027F790` invokes this lookup and makes further indirect
  engine-service calls. Their implementations remain unrecovered.
- **Known runtime global layout** now includes registry pointer
  `0x0049CAA0`, frame state `0x0049CAA8`, record global

## Local use of the new independently written native tools

The user must provide the original APK locally; the Windows/Linux CI binaries contain **no game content**. After installing the APK's `assets/` with `ds_asset_install`, use these programs on extracted local files:

```sh
ds_m3g_probe "<your local texture.m3g>" --decode-image
ds_m3g_texture_extract "<your local texture.m3g>" "<new output.png>"
ds_im_mesh_extract "<your local model.m3g>"                 # counts-only mode
ds_im_mesh_extract "<your local model.m3g>" "<new output.obj>"
```

`ds_im_mesh_extract` supports the verified simple position/triangle-list subset, not all 91 model resources. Even a valid OBJ can have incorrect winding, orientation or missing textures without full loader verification. No original data is included in the utilities.
