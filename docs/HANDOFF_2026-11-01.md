# Dead Space Mobile — Native Windows/Linux PC port handoff

## Native original-resource registration update — 2026-11-01

The real APK's entire ARM `0x284178` control flow is now inspected,
including `0x2839C8` precheck, conditional `0x283F5C` removal,
`0x281DF4` temporary string construction, byte conversion via the
original table at GOT slot `0x004909F4`, `0x2837B4` pair insertion,
and local destructor calls. Native C++17 preprocessing is committed
in `src/original_resource_registration.cpp` and is invoked **27
times** by the existing stage-zero path.

The original `0x2838EC` search routine and `0x2837B4` insertion
routine compare string keys by bytes, maintain an ordered tree and use
ARM32-specific tree node allocation. `OriginalNativeResourceMap`
reconstructs the **observable key/value lookup and replacement
behavior** with a real native C++ ordered tree; it does **not** pretend
to reproduce the original in-memory ARM node layout. It stores
converted names and descriptor values from original private mapped
game data; no game strings, copyrighted binaries, or data are bundled.
The original `0x2839C8 -> 0x283F5C -> 0x2837B4` flow now has an
optional native resource-map path that eliminates those three
unimplemented callbacks. Tests confirm bytewise key comparisons,
replacement, all 27 registrations, and fail-closed string/table
mapping. Native C++ heap string storage replaces the original
`0x281DF4` ARM allocator.

**Engine state is not initialized yet.** The native resource table
covers registration behavior only. Resource query function
`0x2803E4` and many related original engine systems still require
native translation. The original allocator/service virtual methods
and renderer likewise remain incomplete. No test-only success may be
used to advance the engine state.

## Original event-record Bionic import resolved and implemented

GitHub real-APK research run
[41315489703](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41315489703)
proved ARM PLT entry `0x00035194` resolves through GOT
`0x0049031C` using `R_ARM_JUMP_SLOT` to **`__atomic_swap`**.
The original event constructor `0x002807A0` supplies r0=0 and
r1=the new event record +4. Android Bionic source documents
`__atomic_swap(int new_value, volatile int *addr)`. The original
return value is ignored by this constructor. The native x86-64 C++17
implementation now serializes the zero-word exchange with a mutex
and the host-mapped ARM memory's byte representation before it stores
the final vtable. It does not load Android or ARM code at runtime.

This eliminates the previously unresolved `constructor_import`
function pointer from `OriginalInputServices` and the separate
`ConstructorRefused` status. Real input still requires the
unreconstructed original virtual pool allocator and event queue.
Cross-platform tests check the complete allocation -> atomic zero
-> record stores -> queue sequence, including nonzero initial values.

Evidence: Android Bionic's public legacy `__atomic_swap` definition
at https://android.googlesource.com/platform/bionic/+/a27d2baa0c1a2ec70f47ea9199b1dd6762c8a349/libc/bionic/atomics_x86.c


## Native original JNI input reconstruction (2026-11-01)

The actual APK's ARM32 code has been verified on GitHub runner
([original research](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41313773557),
[complete handler traces](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41313898511)):

| Entry | Original ELF VA | Native status |
| --- | --- | --- |
| Raw pointer down | `0x0027F958` | complete native JNI leaf, returns `0x6000C` |
| Raw pointer move | `0x0027F964` | complete native JNI leaf, returns `0x4000C` |
| Raw pointer up | `0x0027F978` | complete native JNI leaf, returns `0x8000C` |
| NativeOnPointerEvent | `0x0027F9B4` | native record allocation/fields/event dispatch; external virtual method bodies remain |
| NativeOnKeyDown | `0x00284828` | native record allocation/fields; queues event `0x40008` |
| NativeOnKeyUp | `0x00284770` | native record allocation/fields; queues event `0x80008` |
| Input record constructor | `0x002807A0` | native vtable `0x00489828` -> original imported helper `0x00035194` -> vtable `0x00489840` |

Record size is exactly `0x30`, owner pool allocator call uses
vtable +`0x0C` with stack args 8 and 0, and the queued event uses
queue vtable +`0x20`. Pointer records store module at +`0x10`,
float32 x/y at +`0x18/0x1C`, and pointer ID at +`0x20`.
Keyboard records store module at +`0x10`, Android key at +`0x18`,
and altPressed at +`0x1C`. All original handlers return immediately
if the ARM `0x27E97C` readiness check is false.

`src/original_input_events.cpp` implements the verified native record
and dispatch path; `src/original_input_jni_bridge.cpp` binds the
original exported JNI functions directly to it in x86-64 C++.
`src/original_pointer_jni_exports.cpp` adds the three complete original
leaf return functions. Controlled host CTests validate queue calls,
record layouts, zero-ready behavior and failure paths. Nothing loads an
ARM library, creates an Android runtime or fakes a game scene.

Remaining **actual runtime** dependencies are the original pool
allocator (virtual +`0x0C`), the unresolved imported constructor
helper `0x35194`, the original event queue virtual method (+`0x20`),
and the complete world/render/simulation engine. The new JNI layer
does not make the game playable on its own.

This work builds on function-name and event-constant comparisons with
Volodymyr Atamanenko's MIT-licensed Vita project, but all ARM machine
instructions and static addresses were independently recovered from
our own different APK. Preserve upstream credit and don't import the
Vita ARM loader.

## Research integration: v-atamanenko/deadspace-vita (source reviewed 2026-11-01)

The [Dead Space Vita port](https://github.com/v-atamanenko/deadspace-vita)
by Volodymyr Atamanenko, based on Andy Nguyen's ARM .so loader, is
**not** a native recompilation. It maps and executes the **Xperia Play
ARMv6 build v1.1.33** on PS Vita; the loader explicitly requires
`lib/armeabi/libEAMGameDeadSpace.so` with original SHA-1
`0ed42b611415015807f759ec9b5457857143ce39`. **This is not
evidence that that game's ELF offsets, ARM patches or vtables match
the separate user-confirmed Dead Space Mobile Fixes APK.** Do not
merge its loader/so_util/kubridge/VitaGL or patch offsets into our native
x86-64 rebuild, and do not redistribute either original game binary.

Verified cross-port architectural findings, with upstream sources:

- `loader/main.c`: startup order
  `JNI_OnLoad -> EAAudioCore__Startup -> NativeOnCreate ->
  NativeOnSurfaceCreated -> NativeOnVisibilityChanged -> NativeOnDrawFrame`
  and input polling after the first two frames. These are observations
  about the Xperia Play edition, not proof of the other edition's
  game-loop behavior.
- `loader/reimpl/io.c`: `appbundle:/`, the original Android
  `Android/data/com.ea.deadspace/files/` sandbox, and
  `deadspace/published -> assets/published` path conventions.
  The Vita loader also requires `published/data/achievements.sb`
  for its edition. This marker is *optional evidence* in the native
  desktop port, not a universal requirement.
- `loader/reimpl/controls.c` and `loader/reimpl/controls.h`:
  original input entry points `NativeOnPointerEvent`,
  `NativeOnKeyDown/Up`, and `NativeOnAcceleration`.
  Joystick input is synthesized into virtual touch positions,
  including the right-stick touchpad; Zero-G movement may depend on
  an acceleration gesture. Map these to native keyboard/mouse controls
  only after matching the APK's code.
- `loader/patch.c`: Xperia-specific hardcoded ARM modifications
  deliberately **excluded**; they are not portable game logic.
- `LICENSE`: MIT license. All upstream technical findings are credited
  here; the new C++ path resolver is independently authored.

Integrated native code:
`src/deadspace_paths.cpp` / `include/ds_port/deadspace_paths.hpp`
translate *user-owned* private installed APK assets to portable host

## Local use of the new independently written native tools

The user must provide the original APK locally; the Windows/Linux CI binaries contain **no game content**. After installing the APK's `assets/` with `ds_asset_install`, use these programs on extracted local files:

```sh
ds_m3g_probe "<your local texture.m3g>" --decode-image
ds_m3g_texture_extract "<your local texture.m3g>" "<new output.png>"
ds_im_mesh_extract "<your local model.m3g>"                 # counts-only mode
ds_im_mesh_extract "<your local model.m3g>" "<new output.obj>"
```

`ds_im_mesh_extract` supports the verified simple position/triangle-list subset, not all 91 model resources. Even a valid OBJ can have incorrect winding, orientation or missing textures without full loader verification. No original data is included in the utilities.
