### Verified code, November 1, 2026

- **29 exact original JNI integer-return functions** are individually exported
  from `src/original_jni_exports.cpp` and verified against original
  instruction-immediate values. Windows/Linux CTests pass.
  [Real-APK equivalence run](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41296566517).
- **The separate original `Java_com_ea_DeadSpace_DeadSpace_runEntryPoint`
  JNI export is an actual zero-return stub**, NOT the game loop:
  original ELF address `0x00035de8` calls `0x0027e974`, which executes
  `MOV r0,#0; BX LR`. Native C++ is in `src/original_game_entry.cpp` and
  unit-tested; no ARM runtime required.
- **ARM frame dispatcher recovered** from original JNI export at
  ELF `0x0027f008`, a direct unconditional B to `0x0027ef68`.
  This is an actual ~39-instruction routine with an original state word at
  offset 0 of a global object. If state is 0, it calls native routine
  `0x0027f870` with context pointer `object+8`, then stores state=1.
  State=1 calls `0x0027fc68` with the same context; other states immediately
  return. The separate state-1 branch calls `0x0027eecc` when the active
  routine returns zero, otherwise dispatches two indirect vtable calls.
  **The latter callees/side effects are not fully reconstructed.**
- The proven state-0 path, strict rejection of unimplemented state-1
  execution, and state selectors are independently ported in
  `src/original_frame_dispatch.cpp` and tested in
  `tests/original_frame_dispatch_tests.cpp`. The C++ port does not
  pretend that the full original frame is playable.
- **Additional original code behavior:** ELF native routine `0x0027f870`
  calls `0x0027f790` then tail-branches to `0x00280520`, passing the same
  `object+8` pointer to both. An evidence-backed native C++ dispatch
  sequence is implemented, but the two called routines themselves remain
  missing; unresolved function pointers are rejected rather than
  substituted. Native routine `0x0027fc68` calls an object's vtable[0]
  method and normalizes its result to 0 only if the original return is 1;
  otherwise it returns 1. This return transformation is ported and tested.
- **Recovered original signed 64-bit clock-value arithmetic** from
  ELF native function `0x00280520`: conditional `[object+0x40] OR
  [object+0x44]` zero guard; only if both are zero does the original call
  clock source `0x000357c4` and compute signed
  `large_component*1000000 + small_component` using ARM
  `ASR/SMLAL`, storing the 64-bit result little-endian at
  `[object+0x40]` with `STRD`. Independently authored portable C++ in
  `src/original_timing_math.cpp` reconstructs the exact integer computation,
  offset and zero-slot guard. Unit tests cover zero guard, repeated calls,
  negative values, integer extremes, bounds and absence of memory clobbering.
  **The original clock-source function is NOT yet reconstructed**;
  the C++ accepts the two source values rather than manufacturing time.
  [Real original APK instruction proof](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41298512403)
  and later stricter clock-guard verification on GitHub Actions.
- [Original ELF ARM instruction proof](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41298083923):
  original APK on hosted runner, bounded Capstone disassembly, exact
  instruction and state-branch validation, no original bytes bundled.
  Cross-platform C++ CTests: [build run 41298045331](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41298045331).

### Address-mapping correction (critical)

**The Ghidra importer uses a +0x10000 address bias relative to the original
ELF virtual addresses.** For example:
`Java_com_ea_DeadSpace_DeadSpace_runEntryPoint` is ELF `0x00035de8` but
Ghidra `0x00045de8`. Likewise, the original frame target is ELF
`0x0027ef68` but Ghidra `0x0028ef68`. An earlier Ghidra trace of
`0x0027ef68` mistakenly examined an **unrelated function** starting
`0x0027ead0` in Ghidra. Do not use that older 295-instruction function
as the game update loop. The correct Ghidra frame trace is
[run 41297365311](https://github.com/daniyalshakeel5/Dead-Space-Mobile-PC-port/actions/runs/41297365311);
the ELF section and PT_LOAD address mappings are independently checked.

## Local use of the new independently written native tools

The user must provide the original APK locally; the Windows/Linux CI binaries contain **no game content**. After installing the APK's `assets/` with `ds_asset_install`, use these programs on extracted local files:

```sh
ds_m3g_probe "<your local texture.m3g>" --decode-image
ds_m3g_texture_extract "<your local texture.m3g>" "<new output.png>"
ds_im_mesh_extract "<your local model.m3g>"                 # counts-only mode
ds_im_mesh_extract "<your local model.m3g>" "<new output.obj>"
```

`ds_im_mesh_extract` supports the verified simple position/triangle-list subset, not all 91 model resources. Even a valid OBJ can have incorrect winding, orientation or missing textures without full loader verification. No original data is included in the utilities.
