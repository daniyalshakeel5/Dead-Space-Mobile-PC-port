### End goal and nonnegotiable constraints

Rebuild *Dead Space Mobile* for **native x86-64 Windows and Linux** in
C++/CMake, full keyboard and mouse controls in the spirit of the original
PC Dead Space releases, optimized for lower-end hardware. The user explicitly
does **not** want an Android emulator, running the ARM executable under an
instruction translator, or merely a compatibility-layer wrapper.

Game assets must come from a **user-owned original APK supplied locally**,
not from public GitHub commits, releases, or bundles. Do not publish
copyrighted game assets or extracted Android native libraries.

**Reliability:** Previous attempts to process archives in the assistant's
local VM caused `ClientError`/tool failures. Keep heavy work—including
decompilation, real asset extraction, compilation, tests and releases—on
GitHub Actions or the user's own machine. Use GitHub's connected actions for
lightweight file reads, commits, PRs, CI logs and audits. Avoid repeatedly
attempting heavy local Python/container processing.

3. **No original x86-64 engine exists.** No verified game entrypoints,
   update loop, scene renderer, camera, game physics, collisions, AI, weapon
   handling, animation, audio, missions, UI or gameplay behavior have been
   ported.
4. The resource scanner reports possible file signatures, not decoded
   proprietary resource formats or proof of game engine integration.
5. The local installer copies raw compressed resource files from
   `assets/`; it does not understand or display them. It supports ZIP32
   and method 0/8; ZIP64 or unsupported archives can fail closed.
   CRC32 is not a cryptographic authenticity check; APK signatures are
   **not** verified.
6. No authentic APK visual, audio, asset-reader, or gameplay comparison has
   occurred. Never label the port playable or engine functions native-verified
   based solely on green synthetic CI.

## Existing private research workflow

`.github/workflows/deadspace-research.yml` has an optional
`workflow_dispatch` path using the GitHub Actions secret `DS_APK_URL`:
an HTTPS short-lived **private** URL to a legitimately held APK. In a manual
run the runner downloads it to temporary storage, runs
`tools/deadspace_audit.py` and `tools/deadspace_asset_recon.py`, and
publishes only aggregate `report/*.json`; never game files or binaries.

**Caveats:**

- The workflow is still in a draft PR; GitHub manual dispatch typically
  requires the workflow file to exist on the default branch. Do not silently
  merge without coordinating changes and CI state.
- No `DS_APK_URL` has been confirmed configured. The successful push/PR CI
  runs used synthetic fixtures and repository-only inventory. Do not claim
  the private analysis step ran because the workflow is green.
- Private temporary URLs and APK data must not appear in commit history,
  comments, logs, public artifacts, or releases.

For local-first research, a user who has their own APK can run:

```sh
python3 tools/deadspace_asset_recon.py --apk "/path/to/owned.apk" --output "resource-recon.json"
```

Inspect the JSON before sharing. It reports aggregate groups and an APK SHA-256,
not raw game assets or individual entry filenames.

## What to do next (in priority order)

1. **Recover genuine evidence.** Obtain a privacy-safe resource/ABI report
   from the **original, user-owned APK**, either using the local scanner or
   a manual private GitHub runner workflow. Confirm package hash, ABI, native
   library inventory, resource grouping and suspicious packed containers.
   Distinguish true findings from clues and guesses.
2. **Map original code/data boundaries.** Privately inspect actual native
   entrypoints and Java/JNI bridge. Identify real routines that read assets
   and initialize graphics/input. Reverse-engineer enough to document
   precise file formats and source behavior. Do not publish proprietary
   binaries or decompiled game source.
3. **Choose ONE evidenced resource family** (e.g., a verified texture or
   archive container). Implement its original format parser in portable C++
   with strict bounds and synthetic regression tests; test against the user's
   actual files privately. Avoid placeholder/mock game behavior disguised as
   original functionality.
4. **Add a native renderer and scene path** only when enough genuine format
   evidence exists. Connect verified asset decoding with an SDL2/OpenGL
   desktop harness; test first asset rendering before physics or AI.
5. **Integrate input/timing deliberately** with original action/animation/
   update semantics. A host tick of 60Hz is not a license to run the original
   simulation at 60 FPS without correcting frame-based behavior.
6. **Keep CI authoritative.** Commit each cohesive change to the current
   development branch, run Windows/Linux CMake/CTest on GitHub and examine
   individual job logs. Keep unverified subsystems labeled as such; do not
   invent test outcomes, releases, or download links.
